# 传输诊断

## 请求边界

服务协议与 Base URL 显式配置。Chat Completions、Responses 与 Gemini 使用不同路由和请求字段；服务端支持某一路由，不表示其他协议路由也存在。模型名、搜索工具和思考参数必须被当前渠道接受。

插件可通过 Node HTTP 或 renderer fetch 保持流式连接，等待完整结果后一次性进入业务处理。选择在请求前固定，不因传输失败静默重发到另一通道。非流式使用宿主请求能力。

## 诊断顺序

1. 核对实际目标库、插件版本、协议、Base URL、模型和所选传输。
2. 对照插件的安全错误信息与服务端请求日志，确认请求是否到达、路由是否匹配，以及终止发生在响应头、首内容或流完成的哪个阶段。
3. 核对搜索、思考参数和渠道能力，避免用不同配置的成功请求证明失败请求应当成功。
4. 检查客户端超时、反向代理读取超时和服务端保活；分别测量响应头及首个有效内容的时间。
5. 请求结果未知时先查服务端状态；由用户确认后再手动重试。

HTTP 成功状态不代表正文完整。流截断、JSON 不完整、明确 API 错误和 Provider 结果未知分别处理。请求账本只属于当前进程，不证明跨重启的计费状态。

## 保活与中转

流式连接有助于在等待生成时保留连接；实际效果取决于中转是否在首内容之前发送可见心跳，以及代理是否刷新这些字节。仅配置保活间隔不能证明首内容之前已经发送心跳。非流式保活不能直接替代 SSE 心跳。

为中转修改配置时，先确认部署程序与版本实际识别的配置项，再以同一路由、模型、搜索和思考参数复测。客户端超时与服务端取消应分别看日志，不能只凭某一个状态码判定根因。

## 工具与记录

`scripts/build-host-diagnostic.mjs`、`scripts/diagnose-host-transport.js` 和 renderer 探针用于宿主诊断。运行前核对命令支持的参数，输出放项目 tmp/。只记录必要的请求形状、耗时、状态与脱敏错误，不输出密钥、认证头、完整个人设置或私人正文。

离线解析和探针测试只证明受测边界行为。真实请求需单独授权并报告模型、协议、服务和结果；服务端维护交给掌握部署环境的维护者完成。
