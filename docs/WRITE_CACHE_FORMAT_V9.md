# 同类型固定 Write 输出格式（v9）

本次候选针对已验证的路径：精确模型 `gpt-6.1-sol`、OpenAI Responses、提示缓存开启。每种知识类型使用一个固定输出 Schema，当前任务用 `<write_stage>` 选择阶段。其它模型、别名、协议及缓存关闭路径继续使用原阶段格式，没有新增设置或自动付费回退。

## 输出与接受规则

API 返回 `{"result":{"stage":"core",...当前阶段字段}}`。固定 Schema 的嵌套 `anyOf` 保留各阶段的原字段、枚举、必填和封闭对象；API 可生成该类型的任一合法阶段。应用先检查外壳和当前 stage，再用原阶段 Validator 检查字段。错阶段、缺字段、多字段或解析失败均不提交结果，也不自动再请求。这保留应用的接受约束，但 API 的允许阶段范围比旧单阶段 Schema 更宽。

业务草稿、笔记渲染仍只接收内层原字段。完整原始封装文本、原生 Responses 输出顺序、引用及其偏移保持原样用于续写。去重只读取经原阶段校验的历史字段，且必须与当前草稿值精确一致；修改值、部分历史和未知内容都保留需补的草稿。版本 v9 隔离旧历史、原生状态、response ID 和缓存路由 key，已经验证的草稿及待提交结果仍按原恢复流程保留。

14 份阶段模板和业务字段 Schema 没有改动。本轮从 v8 升级不需要更新个人提示词；更早默认模板的维护仍使用原 `scripts/update-write-defaults.mjs`，未知定制继续整批拒绝。

## 实验依据

无新搜索的 A→A→B→B 对照中，四个 body 除 `text.format` 外逐字段相同。A 的报告缓存从 4224 升至 7168，切换格式后的 B 为 4224，B 再次同体请求升至 6912。B 的报告未缓存输入从 2765 降至 77。这支持格式变化影响可复用前缀；上游账户/节点身份未观测，不能仅凭数值定位具体前缀。

图论完整三阶段对照使用公开资料、原任务深度、high、原输出策略及实际 renderer-fetch/180000ms；保留相同工具定义，两臂禁止新搜索。六次交错请求全部完成，无重试，各自保留独立真实原生历史。

| 三阶段汇总 | 原阶段格式 | 固定格式 |
|---|---:|---:|
| 报告输入 tokens | 33156 | 36825 |
| 报告缓存输入 tokens | 12672 | 24448 |
| 报告未缓存输入 tokens | 20484 | 12377 |
| 报告输出 tokens | 10986 | 11163 |

本例未缓存输入少 8107（约 39.6%），总输入多 3669，输出多 177。固定格式缓存依次为 4224/8192/12032，原格式为 4224/4224/4224。匿名全文评审在揭盲前接受两臂：主干覆盖、证明和算法深度、分类主轴没有实质退步；不据此声称所有类型或自动检索场景都节省账单。

设每 token 价格分别为未缓存输入 U、缓存输入 C、输出 O，该例差额为 `-8107U + 11776C + 177O`；只有该值小于 0 才更便宜。服务实际费率未知。缓存比例不等于费用节省率；固定 Schema 增大首次输入，独立生成的历史也不同。

含自动检索的概率论对照仅前四笔完成，第五笔达到真实 180 秒策略后终态未知，第六笔未发送。较早非流式实验另有独立 HTTP524 未知请求。两笔均未重放，用量不能记为 0。自动检索轨迹和完整收益尚未证明，不以硬限搜索、降低输出深度或放松业务校验换取缓存比例。

## 验证与安装

永久测试覆盖五类型全部阶段、错阶段和非法字段、原生与引用偏移保真、旧版本/不同模型和端点隔离、预填草稿、真实队列及笔记投影、已付费 checkpoint 崩溃重载后本地提交。正式候选的宿主 API0 验收使用当前 PromptManager 与实际产品写作器，原库、配置及队列不参与合成写入。

发布及安装状态以发布记录为准。更新插件前确认没有活动任务，正常停用后替换并启用，保留原数据、队列和个人模板。权限拒绝时停止；不修改 ACL，也不丢弃编辑状态。

## 本地提交失败后的重启保护

模型返回并通过校验后，任务结果先保留在内存，随后写入工作流 checkpoint。若第一次 checkpoint 保存失败，队列仅持久一个 `resultPendingCommit: true` 标记，不保存模型正文、提示词、凭据或原生状态。

同进程还有结果，或磁盘已有该阶段的有效 checkpoint/已应用记录时，继续本地提交，不再次请求模型。重启后没有可恢复结果时，普通和批量重试被阻止，显示 E322；只有明确确认重新发送才允许新请求。旧的存储失败记录在无法证明本地结果存在时也保守处理。若之后恢复了同阶段的有效 receipt，E322 可恢复为本地执行；普通 Provider 未知结果或取消状态不会因此解除保护。

标记本身保存也可能失败。此时此前的 running 记录按原恢复规则转为需确认状态，不能声称任何崩溃窗口都绝对不会重复请求。旧版本的队列读取器不识别新标记，回退旧代码可能安全拒绝恢复该失败队列；需使用配套新包或升级前保留的队列备份。正常完成会移除标记。
