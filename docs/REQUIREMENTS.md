# Cognitive Razor 需求基线

日期：2026-09-28

用途：判断当前插件代码是否符合你已经说过的真实需求。本文只记录有出处的要求。代码里多出来的行为写在文末「未确认能力」，不升格成需求。

对照时读 [DESIGN.md](DESIGN.md)。哲学立场读 [PHILOSOPHICAL_FOUNDATIONS.md](PHILOSOPHICAL_FOUNDATIONS.md)，那份宪章不是功能清单。

## 怎么读

每条需求有四种标记：

| 标记 | 含义 |
| --- | --- |
| 已确认 | 项目记录里写明已经和你确认，或你后来明确选过 |
| 已取代 | 早期说法已被后一次确认推翻，不能再拿来验收 |
| 宪章 | 你写在哲学文档里的原则，还没有变成可勾选的功能 |
| 未确认 | 代码有这项能力，但现有记录里没有你的确认 |

助手从代码反推出来的行为，一律不算已确认。

出处主要是 `task_plan.md` 的「个人外置大脑需求（已与用户确认，2026-09-21）」，以及 2026-09-27 你对「完整卡片流程 + 独立已中断状态」的选择。2026-09-22 评估里被点名取代的旧说法，下面单独列出。

## 术语

- **节点**：带 Cognitive Razor frontmatter 的知识笔记。身份由名称、类型和知识关系共同确定。同名但类型不同，是两个节点。
- **五类本体**：领域、议题、理论、实体、机制。
- **创建工作流**：你确认类型之后，插件持久创建节点并依次写作。Define 本身只是确认前的候选，不是队列阶段。
- **记忆卡片**：从节点正文生成、追加到镜像 `-decks.md` 的理解检查材料。它不是创建工作流的一个阶段。
- **理解下限**：能检查定义、机制、条件、例子、比较、应用和常见误解，不以背诵原文为目标。
- **推演情境**：模型根据正文概念构造的新例子或假设。必须标明，不能写成源笔记里的事实。
- **已中断**：请求没有完成，或结果是否已经发生无法确定。不会自动重试。这是你在 2026-09-27 选定的独立终态，不是普通失败。

## 已确认的目的

插件只给你本人用。目标是在学习时把混乱认识整理成可见、可修改的结构化知识。AI 负责整理和核查辅助。「模型同意」不是正确性证明。

## 已确认的需求

### 工作台

- **R1** 当前笔记提供三个入口：拓展当前笔记、事实核查、生成记忆卡片。
- **R2** 生成记忆卡片只处理 Cognitive Razor 节点，沿用拓展和事实核查的节点前置条件。普通 Markdown 不生成卡片。
- **R3** 卡片生成不检查事实核查是否完成。
- **R4** 为当前笔记重新生成向量不是高频操作，入口在设置的维护区，不在工作台。

### 知识模型与创建

- **R5** 五类本体是长期使用的核心模型。仍允许用真实材料验证和调整。记录当时没有明确的缺失类型。
- **R6** 同一名称可以同时存在不同类型的节点，例如「博弈论」既可以是领域也可以是理论。不因同名自动当成重复。
- **R7** 新概念由 AI 给出五类候选，你确认类型之后才创建持久节点。插件不替你决定类型。
- **R8** 节点工作流顺序保持 `Define → Tag → Write → Verify`。
- **R9** Verify 保持当时的现状。不因为记忆卡片增加强制闸门，也不改变原有完成条件。Verify 怎样算完成，记录里仍是未决，见文末。

### 记忆卡片

- **R10** 卡片用来检验理解下限，不追求背诵原文。数量按知识层级和笔记密度决定，不设固定上限。适用时覆盖定义、机制、条件、例子、比较、应用和常见误解，同一维度不为了数量重复。
- **R11** 「不设上限」是内容策略。它不绕过 Provider 的上下文、输出长度或任务超时。这些技术边界应在界面或错误里如实出现。
- **R12** 格式兼容 Obsidian Decks（`dscherdi/decks`）。单次生成可以混用标题卡、双列表格和 cloze。模型按内容选择格式，不统一成一种，也不为了格式种类而堆格式。
- **R13** 结果追加到既有卡片文件。再次生成保留以前内容和你的手工修改。插件不覆盖、不去重、不与历史卡片同步，批次之间不加 Markdown 小标题。
- **R14** 源文件与卡片文件一一对应。两个根目录可配置，默认 `C-知识库` 与 `D-习题库`。子目录镜像，文件名固定追加 `-decks`。例：`C-知识库/1-领域/数学.md` → `D-习题库/1-领域/数学-decks.md`。
- **R15** 发送给模型的是去掉 YAML frontmatter、并去掉插件标记的事实核查报告之后的正文。不按普通标题猜测删除正文。这和向量索引用的排除规则相同，但卡片使用完整正文，不套用向量索引的 12,000 字截断。
- **R16** 点击生成时锁定源路径、正文快照和目标路径。请求期间你再改源笔记或目录设置，本批仍使用入队时的快照和目标。
- **R17** 模型正常返回整批结果后，一次性追加到目标 `-decks.md`。不预览。目标目录不存在则创建。源目录和源笔记只读。
- **R18** 不做 Decks 格式修复，也不因部分卡片格式异常而整批拒绝。格式问题由你在 Decks 复习时发现并手改。实现只保留空结果和明显不是可追加 Markdown 的保护。
- **R19** 卡片是独立队列任务，不并入 Define、Tag、Write、Verify，不写回源笔记。
- **R20** 允许模型构造新例子或假设情境，提示词必须要求标明「推演情境」或「假设」。
- **R21** 卡片使用独立模型配置，不复用 Verify 或其他任务的模型，也不继承默认模型。未配置时要提示先配置。
- **R22** 卡片提示词固定在插件代码里。设置页不提供完整提示词编辑器。
- **R23** 取消或中断时，本批任何卡片都不追加。只有整批结果正常返回后才追加。
- **R24** 插件重载时，运行中的卡片任务标为已中断，不自动重试。只有你再次从源笔记生成，才发出新的 Provider 请求。
- **R25** 2026-09-27 已选定：中断是队列里的独立终态，不把这类情况显示成可重试的普通失败。
- **R26** 不为写入失败另做「无 Provider 的重放」。写入故障不作为专门设计的常见路径。
- **R27** 生成成功后不自动打开目标文件，只在工作台反馈结果和路径。

### 提示词真实性

- **R28** 保留现有模板和知识真实性规则，并补上这一区分：字段按知识类型确实不适用时写「不适用」；理论上适用但当前材料不足时写「目前依据不足」或「待核实」。不得用「不适用」逃避材料缺口。

## 已取代、不能再当验收标准的旧说法

这些话曾经出现过，后一次确认已经换掉：

- 「任意当前 Markdown 都能生成卡片」→ 以 **R2** 为准，只处理节点。
- 「卡片输入等同于向量输入」→ 排除规则相同，长度不同，以 **R15** 为准。
- 「写入前做 Decks 结构机械校验，失败则整批不写入」→ 以 **R18** 为准，只拒绝空结果和明显非 Markdown，不做格式修复流程。

## 宪章里的原则

下面五条来自哲学宪章第五章的推导，不是从插件功能倒推的。它们约束「什么样的知识工具才站得住」，但记录里没有把每一条都写成已验收功能。

1. 知识要分类，因为不同类型需要不同的认知操作。分类是暂定的。
2. 知识要能溯源：结论之外，还要能看见依据，哪怕依据是「尚未验证的直觉」。
3. 知识要有有选择的、带语义的关联。AI 可以建议关联，确认仍由人做。
4. 修订是一等操作：允许修改，留下改了什么，破坏性修改前要能预览和回退。
5. 判断主体是人。AI 输出是建议。接受和拒绝的成本应当对称。高影响操作要经过人的确认。

和已确认需求直接撞上的一点：**R17 明确要求卡片不预览、直接追加**。这收窄了第 4、第 5 条在卡片这条路上的适用方式。卡片一旦追加，插件不提供撤回。你要不要把宪章原样用于验收卡片，是当前唯一需要你拍板的问题，见文末。

## 明确未决

- **宪章与卡片直写的优先级**。见下面的问题。

## 未确认能力

这些能力在当前代码里存在。现有需求记录没有你的确认。对照代码时，把它们当成「多出来的实现」，不要默认成你的需求。

- 三种聊天协议：OpenAI Chat Completions、OpenAI Responses、Gemini；嵌入只用 OpenAI Embeddings。
- 语义向量索引、相似度重复检测（默认阈值 0.85）、合并预览后把冗余笔记移入回收站。
- 拓展的两种模式：领域、议题、理论从正文结构做层级拓展；实体、机制做抽象拓展。
- 按类型分目录，默认 `1-领域` 到 `5-机制`。
- 创建时笔记状态从 `seed` 到标签后的 `draft`；核查成功写成 `evergreen`。
- 自动事实核查开关，默认关闭。创建工作流只有在确认当时打开了这个开关，才会在写作后自动进入 Verify。
- 各类型写作字段、阶段顺序，以及提示词里的具体段落结构。
- 队列暂停、批量重试、并发数、Provider 超时和最多 3 次尝试。
- 结果未知的请求不自动重发；明确失败的非卡片任务仍可在确认后单项重试。
- 备份并重置插件运行数据。
- 工作流对话续写、提示缓存、Verify 的联网搜索。
- 插件声明为仅桌面端。

## 当前需要你决定的一个问题

记忆卡片要按哪条验收？

推荐按 **R17**：整批返回后直接追加，不预览、不撤回。宪章第 4、第 5 条继续约束创建、合并和核查，但卡片这条路按你 2026-09-21 的明确选择收窄。代价是：错误卡片会留在 `-decks.md` 里，只能由你手改；插件不会帮你撤销。

另一条路是让宪章压过 R17：卡片也必须先预览，接受和拒绝同样容易。那样当前实现就不满足需求，需要改交互。这和你已经确认的「不预览、直接追加」相反。
